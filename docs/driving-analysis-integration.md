# driving-analysis 기능을 현재 제품 UI에 통합

원본 `feature/driving-analysis`의 `a6897f0`(분석·피드백·추천)과 `735e756`(원본 시연 가이드·Virtual Console 스크립트)를 `refactor/chageun-product-ui`에 병합했다. 원본/다른 팀원 브랜치를 수정하지 않는다.

## 기능 대응

| 원본 기능 | 현재 앱에서 쓰는 곳 |
| --- | --- |
| 차량 속도 기록 | 앱이 열려 있고 차량 연결이 활성화된 동안 속도가 들어오면 자동 시작. 시연 시작 버튼과 별개 |
| 차량 신호 퀘스트 | 퀘스트 → 차량 연결. 깜빡이·조향·브레이크 수신과 기존 퀘스트 보드를 표시 |
| 연결 시작 / 주행 기록 마치기 | 차량 연결 화면의 기존 버튼. 기록 종료는 정차 후 제공 |
| `DrivingAnalyzer` | 속도 변화 및 차량 신호 시도를 분석하고 Room 리포트에 점수 저장 |
| `FeedbackWriter` | 피드백의 요약·잘한 점·연습할 점. 원본 분석·문장 생성 코드를 사용 |
| `QuestRecommender` | 최근 5회 기록의 점수·어려움 메모·차량 보드로 최대 3개 추천. 원본 가중치와 기준 유지 |
| 맞춤 추천 화면 | 하단 퀘스트를 누르면 먼저 표시. 점수와 추천 이유·목표·진행도 확인 |
| 피드백 → 맞춤 퀘스트 | 피드백 아래 버튼. 해당 기록 출처로 추천 연결 |
| 기존 제품 UI | 지도·움직이는 차량/경로·핸들·4개 자동 시연 유지. 6개 영역은 퀘스트 → 종합 기록 |
| 원본 시연 스크립트 | `scripts/demo-harsh-drive.ps1`, `scripts/demo-signal-drive.ps1` |

추천 카드는 상세 설명과 관련 자동 시연으로 연결되며, 실제 차량 퀘스트 보드도 별도로 열 수 있다. 시연을 재생했다고 실제 차량 신호 퀘스트나 개인 점수가 올라가지는 않는다.

## 연결 보완

- 기존 앱의 깜빡이 입력 기본값이 강제 OFF였던 것을 SDK 입력으로 변경했다. 시연 도구를 닫으면 가상 입력을 해제한다. SDK의 RIGHT/LEFT/OFF를 읽어 코치에 반영하며, 실제 방향지시등을 켜는 명령을 앱에서 보내지는 않는다.
- 속도만 수신돼도 기록을 시작한다. 깜빡이·조향각 누락은 해당 동작의 판정을 보류하며 주행 전체를 막지 않는다.
- AAOS 속도는 콜백과 1초 간격의 현재 값 읽기를 병행한다. 연결 세대가 끝난 콜백은 무시한다. 후진 속도는 이동량에 절댓값을 사용하고, 오래된/미수신 속도는 정차로 처리하지 않는다.
- 출발 전 0 샘플의 시각은 UI 루프 시간이 아니라 실제 수신 시각으로 보존한다.
- ‘어려웠어요’에서 영역을 직접 고르고, 메모·STT는 기존 입력 기능을 유지한다. 긍정 메모를 어려움으로 세지 않으며, 영역별 어려움이 추천에 연결된다.
- 감속 점수의 목표를 ‘여유 있게 속도 줄이기’로 표시한다. 이 점수만으로 앞차와의 3초 간격을 확인했다고 표현하지 않는다. 추천 ID·점수·목표 횟수는 원본과 같다.
- 측정되지 않은 주행을 건너뛰어 연속 성공으로 세지 않는다.

## 데이터와 한계

기존 Room 스키마와 사용자 `trips.db`를 보존한다. 추천은 원본과 같이 저장된 리포트·메모·보드에서 조회할 때 계산하며, 별도의 생성형 AI나 추천 퀘스트 인스턴스 테이블을 추가하지 않았다.

기본 추천은 VEHICLE 기록 기준이다. 자동 시연 피드백에서는 REPLAY 메모 기준을 별도로 제공하고, 시연 속도로 실력 점수를 만들지 않는다. 실제 SDK 속도로 가상 경로를 움직인 기록도 개인 주행 점수·추천에서 제외한다. 가상 입력 검증(SIMULATION)은 별도 출처로 남는다.

실제 차량 데이터 수신과 자동차 OEM의 주행 중 앱 허용은 별개다. 실차 배포 승인, 백그라운드 서비스, 실차 하드웨어 검증은 이번 통합으로 완료되었다고 보지 않는다. 현재 기록기는 Activity가 열려 있는 동안 동작하며 다른 앱으로 나가면 미완료 기록을 보존하고 입력 연결을 정리한다.

## 검증

JVM 분석/추천/주행 상태 테스트와 빌드·린트를 실행한다. 네이티브 검사는 각각 별도 DB에서 수행한다.

- `ProductSmokeRunner -e analysis_merge true`: 속도만으로 기록 시작, 출발 0 시각, 피드백→추천, 어려움/긍정 메모 구분, 종합·맞춤·차량 화면 전환, DB 재개방, SDK 수신.
- `-e quest_design true`: 기존 6개 영역, 6회 차선 변경, 주차·하차 이후 결과, 지도 버튼/배너.
- `-e vehicle_quests true`: SDK 수신, 차량 신호 판정·보류·중복 방지·Room 보존.
- 기본 검사: 기존 네 시연과 Pleos TTS, 탭 전환, 기록 보존.
- `-e live_console signal` / `harsh`: 원본 브랜치의 Virtual Console 스크립트를 외부에서 실행하고, 실제 에뮬레이터 SDK 값→주행 기록→점수→맞춤 추천까지 검사한다. 물리적인 실차 검증은 아니다.

이번 환경의 결과: JVM 134개·빌드·린트와 위의 4개 기본 네이티브 검사는 통과했다. Virtual Console 입력 40km/h가 SDK에서 11.11m/s로 들어오고 기록이 시작되는 것은 확인했다. 외부 신호 시나리오는 오른쪽 깜빡이 구간에서 에뮬레이터 시스템 종료 및 QEMU 프로세스 종료로 중단돼 최종 PASS를 얻지 못했다. 이 검사를 성공한 것으로 해석하지 않는다. 기존 AVD 데이터는 유지한 채 재시작했으며 추가 차량 입력 테스트는 중단했다. 원본 브랜치의 시연 성공 기록과 이번 환경에서 직접 확인한 결과는 구분한다.
